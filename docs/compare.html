From v1alpha1 to v1alpha3, and what is proposed next

41 examples of what changes in the Agentic Workflow Protocol, each with the old form on the left, the new form on the right, and the reason for the change: first what is in the v1alpha3 draft, then what pull request #19 proposes and what is planned.

New to AWP? Start with how it fits together. What is shown. The draft chapters compare v1alpha1 with the v1alpha3 draft: the Kubernetes resource model of pull request #16, merged as v1alpha3 by decision D20 on top of v1alpha2 (v1alpha1 plus step iteration, D19). They were first written when that draft was called v1alpha2. The proposal chapters put v1alpha3 today next to what spec pull request #19 proposes (AEP-0023 to AEP-0025), the planned chapter next to a sketch of the AEP-0004 pull request that has no text yet, and the concept chapter next to AEP-0021. Everything is a Draft under review; nothing is accepted except step iteration. All links and checks use the spec branch preview/pr19-pr20 (main plus the open pull requests #20 and #19, not merged text). Snippets marked valid or rejected by checker were run through the reference checker there; proposals are marked not checked.

DraftAEP-0015

Document model

Every manifest becomes a valid Kubernetes resource and stays usable without Kubernetes. Most of this is a mechanical move, done by awp-check.mjs migrate.

1

A minimal workflow

What changes

version and owner move from metadata into spec. Nothing else changes.

Why

In Kubernetes, metadata is ObjectMeta. The API server drops every field it does not know, so a stored v1alpha1 workflow would lose its version and owner, and its digest would no longer verify.

AEP-0015Spec 4.1
2

Governance fields live in spec

What changes

description, classification, purpose, risk, integrity, signature and provenance move to spec as well, with unchanged meaning.

Why

They are governed content: covered by the digest, reviewed and signed. Labels and annotations would have been the only other place in metadata, and governance must never depend on labels.

AEP-0015Spec 4.2
3

Owner is always an object

What changes

The string shorthand for owner is gone. owner always has team (and optionally contact).

Why

A CustomResourceDefinition needs a structural schema: one type per field. "String or object" cannot be expressed. The migration tool expands the shorthand.

AEP-0015
4

Policy conditions have one form

What changes

The plain-value shorthand for equals is removed. Every attribute maps to an operator object.

Why

Same reason as owner: a value that is either a string or an object is not a structural schema.

AEP-0015Spec 8.3
5

Agent manifests

What changes

The same move applies to every kind: Workflow, Agent and Policy.

Why

One rule for all kinds keeps the migration mechanical and the CRDs uniform.

AEP-0015
6

Objects read back from a cluster

What changes

Fields that an object store fills in (uid, resourceVersion, generation, managedFields, ...) are accepted and ignored.

Why

Every object read back from a Kubernetes API server carries them. A validator that rejected them could not check what is actually stored in a cluster.

AEP-0015Spec 4.1
7

The digest survives deployment

What changes

The digest covers apiVersion, kind, metadata.name and spec (without integrity, signature, provenance). Namespace, labels, annotations, store fields and status are not covered.

Why

Deployment tools (Argo CD, Flux, Kustomize, Helm) change namespace, labels and annotations. A reviewed and signed manifest must keep its digest through that. This case is in the conformance suite and verifies.

AEP-0015Spec 9.1
8

status is reserved for runtimes

What changes

A manifest may carry status. Validators ignore it, the digest does not cover it, and runtimes never derive governance decisions from a status they did not write.

Why

The runtime reports there whether it accepted the manifest. kubectl get and kubectl wait --for=condition=Valid read it directly.

AEP-0015AEP-0019Spec 3.11
9

Storing a workflow in Kubernetes

What changes

The repository publishes CustomResourceDefinitions generated from the JSON Schema (schema/crd/), with printer columns and a status subresource.

Why

With a wrapper, the AWP document is invisible to RBAC, kubectl, GitOps health checks and owner references, and every runtime wraps differently. The output on the right was checked on a local k3s cluster.

AEP-0015Spec 3.10
10

x- fields move into extensions

What changes

x- keys are only allowed inside an extensions object.

Why

A structural schema cannot have free keys next to defined fields. This is an interim step: the last chapter proposes to remove x- fields altogether.

DraftAEP-0016

Schedules

What happens when a tick arrives while the previous execution still runs, and when ticks are missed.

11

Overlapping ticks

What changes

concurrencyPolicy is allow, forbid (default) or replace, as in Kubernetes CronJobs. startingDeadline allows one late start after missed ticks.

Why

Overlapping agent executions cost money and can act twice on the same data. The safe default is to skip the tick.

AEP-0016Spec 5.2
12

Skipped ticks are audited

What changes

Every tick without an execution emits trigger.skipped with the reason (concurrencyForbidden, missed, startingDeadlineExceeded). Missed ticks are not replayed in a burst after an outage.

Why

An auditor must be able to see why a scheduled job did not run.

AEP-0016Spec 10.4

DraftAEP-0017

Human input

A workflow or an agent can ask a named person for an answer. Answers are never approvals.

13

Asking a person during a workflow

What changes

A new step type input asks named answerers for free text or a structured answer (a subset of the MCP elicitation schema), with timeout and fallback.

Why

Workflows misused approvals to collect information. An answer is not an approval: it never counts as one, so a free-text reply cannot bypass a governance gate.

AEP-0017Spec 5.8
14

An agent asks a question

What changes

An agent with humanInput may ask the listed answerers while it works, at most maxRequests times. The request and the answer are audited (input.requested, input.provided).

Why

Agents meet ambiguous situations. Asking a named person is safer than guessing, and the limits keep it from turning into a chat.

AEP-0017Spec 5.8

DraftAEP-0018

Step outputs

How a step actually produces the values of its declared outputs, the largest portability gap found by the runtime proof of concept.

15

Outputs of a command step

What changes

The runtime creates an empty directory per attempt and passes it in AWP_OUTPUTS. One file per declared output. At least 256 KiB per output and 1 MiB per step are accepted; outputs of failed attempts are discarded.

Why

Without a rule, an image written for one runtime produces no outputs on another. This was the largest gap reported by the runtime proof of concept (G01).

AEP-0018Spec 5.6.4
16

Outputs of an agent step

What changes

Agent steps end with a built-in tool complete_step that has one parameter per declared output. An agent step with outputs that never completes fails with notCompleted.

Why

Parsing the last message depends on the model following a format. A tool call is structured and checked by the runtime. complete_step is not an action, so it cannot bypass permissions.

AEP-0018Spec 5.6.4
17

Reserved environment variables

What changes

The prefix AWP_ belongs to the runtime; a manifest must not set such variables.

Why

Otherwise a manifest could redirect where outputs are read from, or fake the execution identity a step sees.

AEP-0018

DraftAEP-0019

WorkflowRun and status

A new kind for one execution, and a status shape that existing Kubernetes tools understand.

18

Starting an execution

What changes

A new kind WorkflowRun: creating one starts one execution, as a manual trigger with all its rules. spec.cancel: true or deleting it cancels.

Why

Tools (CLIs, dashboards, pipelines, GitOps) can start and watch executions on any runtime. The actor is never read from the object; it comes from an authenticated source.

AEP-0019Spec 10.8
19

Watching an execution

What changes

The runtime reports phase, pinned workflow, per-step status, usage and the conditions Accepted and Succeeded. No secret values and no output content.

Why

Audit events remain the record; status is the current view for people and tools.

AEP-0019Spec 10.8
20

kubectl shows validity and progress

What changes

The generated CRDs have printer columns for version, owner, the Valid and Ready conditions and the run phase.

Why

Printer columns come from the CRDs, and the CRDs come from this repository. A runtime cannot add them on its own.

DraftAEP-0020

Execution pinning

An execution keeps the manifests it started with, even when GitOps changes them halfway.

21

A GitOps sync during an execution

What changes

An execution uses exactly the workflow, agent and policy versions it resolved at start, until it ends. Mixing is never allowed; a runtime may cancel instead.

Why

An approver approves the step of the version that runs, and the audit trail names exactly that version.

AEP-0020Spec 10.1
22

The digest is required at start

What changes

workflow.digest is REQUIRED in workflow.started.

Why

Name and version can be reused by mistake; the digest identifies the exact content that ran.

AEP-0020Spec 10.3
23

Run exactly the reviewed version

What changes

workflowRef.version and workflowRef.digest are assertions. If the current workflow differs, the run is rejected (versionMismatch, digestMismatch).

Why

A run never selects old versions, so the object store needs no history; the assertion only guarantees that what was reviewed is what runs.

AEP-0020AEP-0019
24

Images: tags in the manifest, digests in the record

What changes

Tags stay allowed outside the security profile. The runtime resolves every image to a digest when an execution starts, pins it like the manifests and records it. For multi-platform images the digest is that of the image index, which works on every architecture. A runtime that cannot run images rejects a command step with image.

Why

Every execution is traceable without forcing authors and packaging tools to maintain digests. Organisations that need the reviewed image to be the executed one choose the security profile.

AEP-0020Spec 9.4

DraftAEP-0022

Step iteration

A bounded fan-out over a list known when the step becomes ready: accepted for v1alpha2 (D19) and part of v1alpha3 as section 5.6.5, combined with the step output interface.

25

One step per item of a list

What changes

forEach runs the step once per item, at most maxItems items and concurrency at a time; each running item run counts against budget.resources.maxConcurrency (default 1). Each item run produces its own outputs through $AWP_OUTPUTS or complete_step; the step output is a JSON list in item order.

Why

The number of item runs never depends on what an item run produces, so budgets and reviews stay bounded. A list longer than maxItems fails the step instead of being truncated.

Step isolation (proposal)

Proposed in spec pull request #19, not applied to the schema: a host syntax for allowHosts, the platform ceiling, enforce or reject, internal destinations and model credentials. Left is v1alpha3 today, right the proposal.

26

One syntax for allowed hosts

What changes

An entry is a host name, a subdomain wildcard *.domain (not the domain itself), an address or a CIDR, each with an optional :port. A bare * or a * in another label is invalid. Names are matched before resolution, addresses after.

Why

Today the forms are undefined (G49), so the same list means different things in different runtimes and cannot be translated into a proxy or network policy.

AEP-0023 (PR #19)Spec 7.5
27

Egress is denied by default under security

What changes

Under the security profile, a manifest without network.egress gets deny. Outside it, the default stays allow.

Why

Deny-by-default deployments and the intent of the security profile conflict with egress: allow as the default (G47). Authors add egress: allow or allowHosts where a step needs the network.

AEP-0023 (PR #19)
28

Enforce or reject against the platform ceiling

What changes

A platform may set a ceiling (per namespace, tenant or installation). The effective network of a step is the intersection of the manifest and the ceiling. If the runtime cannot enforce a rule for a step type, or the ceiling forbids a destination the manifest needs, it rejects before any step runs, and never runs with weaker rules.

Why

An author cannot tell whether a reviewed manifest will run, and a runtime could silently ignore allowHosts (G10, G47, G51). Internal destinations (loopback, private, link-local, CGNAT) are denied after resolution under security unless manifest and ceiling both allow them (G50).

AEP-0023 (PR #19)
29

Model credentials stay out of steps

What changes

Model credentials are runtime configuration. Under security they MUST NOT be visible to steps; outside it, a runtime that exposes them says so in its conformance statement.

Why

A key inside the step can be exfiltrated by any command or prompt injection (G61). A proof of concept keeps keys only at the runtime and gives each attempt a short-lived credential.

Event triggers with CloudEvents (proposal)

Proposed in spec pull request #19: CloudEvents as the event model, equality filters, duplicates, concurrency, rate limits and the actor behind an event. Left is v1alpha3 today, right the proposal.

30

Filters match CloudEvents attributes

What changes

An event is a CloudEvent 1.0. source is matched against the CloudEvents source (the producer, not an adapter), eventType against type. Filter keys are attribute names or data.<path>; values match by equality with the string form; all entries must match, and a missing attribute does not match.

Why

Today the filter is a map of strings with no rule which fields it matches or how (G42, G54). Richer conditions may live in runtime trigger objects, which may only narrow the manifest trigger.

AEP-0024 (PR #19)Spec 5.2
31

Duplicates, concurrency and rate

What changes

The runtime never starts a second execution for the same source and id within a window of at least 24 hours (trigger.skipped, reason duplicate). Event triggers get concurrencyPolicy (default allow) and rateLimit with maxExecutions per period (reason rateLimited).

Why

Brokers and webhooks redeliver; the proof of concept saw a second run for the same event (G43). Today concurrencyPolicy exists only for schedules, so the schema rejects it on an event trigger.

AEP-0024 (PR #19)
32

The person behind an event

What changes

The actor stays system with the authenticated identity of the source. If a source the runtime trusts attests a person, it is recorded as attestedActor, and initiatorCannotApprove and actorCannotApproveOwnAction treat that person as the initiator. A policy can require an attested actor (trigger.attested).

Why

With system as the only actor, a person could start a run by message and approve its own request (G44, a must). Conversation context in event.data is untrusted input and personal data.

State across executions (proposal)

Proposed in spec pull request #19: stores that survive executions, declared in the manifest with classification, retention and access mode. Left is v1alpha3 today, right the proposal.

33

State is declared in the manifest

What changes

spec.state lists stores with name, access (read or readWrite), classification, retention and maxSize. Command steps see them as $AWP_STATE_DIR/<name>, agent steps only through granted tools. Undeclared stores are never exposed; writes are atomic.

Why

Today state lives in a runtime volume that reviewers cannot see, without data class or retention (G03).

AEP-0025 (PR #19)
34

Two workflows of one owner share a store

What changes

Workflows with the same spec.owner in the same namespace that declare a store of the same name share it; the strictest classification applies to every reader; a store of another owner can never be reached. Content read from state is untrusted input (spec 12).

Why

A daily run writes what it found and a chat run reads it and writes preferences (G53); a message stored by one run must not become an instruction for the next (G58).

Event data in the run (planned)

Planned, no draft text yet: a pull request that applies AEP-0004 to v1alpha3 and amends open question 1 of AEP-0019 (G41, G48, G57). The right side is a sketch of the intended result.

35

Event data under its own root

What changes

${{ event.id }}, event.source, event.type, event.time and event.data.<path> become a reference root. dataSchema is validated before the run starts, and classification enters every operation that reads the data. A workflow without an event trigger may not use event.*.

Why

D7 decided an own root instead of mapping events to inputs, which hides that a value comes from an external sender (G41). AEP-0004 is in Review for v1alpha2 and not applied to v1alpha3 yet.

AEP-0004 (planned)Spec 3.9
36

A run that carries its event

What changes

The run object carries the event: origin: ingress when a trusted router creates it, origin: replay for a test or replay, where the actor is the creator and the data is validated against dataSchema. Field names are a sketch of the planned amendment.

Why

Event runs created by an external router fit neither role of spec 10.8 (G48), and event-only workflows cannot be tested conformingly (G57). This is open question 1 of AEP-0019.

ConceptAEP-0021

Extension model (concept)

A proposal, not applied to the schema: replace x- fields with the extension model of the Kubernetes Gateway API. Left is the draft (now v1alpha3), right the proposal.

37

A vendor-specific step

What changes

Closed step types plus type: extension with an extensionRef to an object validated by its own CRD. A runtime that does not know the kind refuses the workflow (ResolvedRefs=False); an extension step is never skipped. It is an action under permissions, policies and approvals.

Why

A runtime that ignores an x- field runs the manifest with fewer restrictions. That is why AEP-0011 (requiredExtensions) was needed. A typed reference fails closed by construction. Same pattern as Gateway API ExtensionRef and Tekton CustomRun.

AEP-0021
38

Policies attached by the platform team

What changes

Policy gets targetRefs to workflows (or single steps via sectionName) in the same namespace. include stays for author-chosen policies.

Why

Policy attachment as in the Gateway API (GEP-713). AWP policies only restrict, so all attached policies simply apply together; no conflict rules are needed.

AEP-0021
39

Runtime configuration stays out of the manifest

What changes

Placement, images, model endpoints and secret mapping live in a runtime-specific binding object that attaches with targetRefs. One accepted binding per workflow and runtime; the oldest wins, others get Conflicted.

Why

The manifest stays portable and its digest unchanged. Fields that decide where credentials, data or network traffic go must be limited by the operator (an allow list), not by the binding author: the proof of concept found a provider key leak through baseURL.

AEP-0021
40

Vendor values carry a domain

What changes

Bare values belong to AWP; implementation values use a DNS prefix and are Implementation-specific. Applies to model providers, secret sources, event sources, audit event types and condition types.

Why

Domain names are unique without a registry, so the extension prefix list (D12) is no longer needed. Same rule as the Gateway API and Kubernetes condition types.

AEP-0021
41

Typos are caught at apply time

What changes

The CRDs drop x-kubernetes-preserve-unknown-fields, prune unknown fields and get CEL rules (x-kubernetes-validations). No admission webhook is needed.

Why

Fixes G09. The Gateway API removed its webhook in favour of CEL. CRD validation is feedback, not a security boundary (GEP-922), so runtimes keep validating.

AEP-0021

Examplecharts/concert-scout

Try it: a complete workflow as a Helm chart

A full workflow of the draft (written as v1alpha2, now v1alpha3) that checks venue programs for new concerts, rates them against a music taste (Metalcore, Metal, Hardcore and related genres by default) and sends a summary. The chart shows OCI registries as one way to transport AWP manifests and ships the CustomResourceDefinitions. It contains no runtime: without one, the objects are stored and nothing runs.

What it shows

Command steps with outputs in $AWP_OUTPUTS, agent steps that end with complete_step, a schedule with concurrencyPolicy, an included Policy, budgets, and an optional WorkflowRun per release.

Why Helm

Helm labels and the release namespace are not covered by the AWP digest, so packaging does not change the identity of the workflow. The VALID and READY columns stay empty until a runtime reports status.
