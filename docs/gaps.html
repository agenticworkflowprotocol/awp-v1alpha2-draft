Runtime feedback: open gaps in the v1alpha3 draft

What a Kubernetes runtime proof of concept and a reference concept still miss in the v1alpha3 draft: 21 gaps, each with what the draft says today on the left, a sketch of the proposal on the right, and what happened in the proof of concept.

These are proposals from one runtime, not accepted specification and not part of the draft. The classification, verdicts and targets are agreed between the runtime side and the spec side; the maintainer still decides. AEP-0023 to AEP-0025 are written and open for review in spec pull request #19 (not merged); the guide summarises what they add. Everything is compared against the v1alpha3 draft (formerly the v1alpha2 draft, b8a0ee8) as previewed on the spec branch preview/pr19-pr20: main plus the open pull requests #20 and #19, not merged text. Pull request #16 was merged as v1alpha3 by decision D20, v1alpha2 is now the step iteration draft (D19). Gaps the draft already resolves (G01, G07, G08, G40) are on the side-by-side page. Left snippets marked valid or rejected by checker were run through the reference checker; proposals are marked not checked, and their field names are sketches unless the source names them.

  • ABelongs in AWP: what a workflow needs and may do, and what its fields mean, portable across runtimes.
  • BAn AWP rule enforced by the platform: the spec says "MUST enforce or reject" in one sentence and names no mechanism, so the platform picks it (NetworkPolicy, Istio, an egress proxy, an operator).
  • CPlatform only: an implementation detail, at most an informative note.

Proposal

Proposed order

AEP-0023 to AEP-0025 are assigned numbers; the AEP drafts are open for review in the spec pull request below.

  1. Now, in the current draft: apply AEP-0004 and amend AEP-0019 for its open question 1 (G48, G57). Small, and it unblocks event runs.
  2. AEP-0023 "Step isolation: network and credentials" (G10, G47, G49, G50, G51, G61). G50 and G61 are security holes, so early.
  3. AEP-0024 "Event triggers with CloudEvents" (G42 to G46, G54, G56), using AEP-0004 and AEP-0019; G52 through AEP-0021.
  4. AEP-0025 "State" (G03, G53, G58), once state is wanted in the current draft.
  5. Into existing AEPs: G52 into AEP-0021, G55 into AEP-0012, G59 and G60 into AEP-0008 (after the current draft), G34 earlier, in the current draft.
  6. Fix now: the triggers[].source row in AEP-0021 B4 (G54), and state as untrusted input in spec 12 (G58).

Events and triggers

Event triggers exist in spec 5.2, but the event itself does not reach the execution, and filters, duplicates, actors and run objects for events are undefined. The proof of concept starts runs from chat mentions, webhooks and MQTT through an event router.

G41

Event data cannot reach the execution

A
Verdict
must, decided (D7)
Target
apply AEP-0004 in the current draft

An event trigger starts an execution, but nothing in the run can read the event: section 3.9 knows only inputs, steps and execution. A chat message that starts a run cannot pass its text, author or thread to the agent.

Why: in the proof of concept

Chat mentions, webhook payloads and MQTT messages started executions in the proof of concept. With no event context, it maps event fields to workflow inputs, which hides that the value comes from an external sender.

Status against the draft

Decided by D7: events are not mapped to inputs. AEP-0004 (Review) replaces the input mapping but is not applied to the spec yet. The proof of concept still maps to inputs (concept E22).

G42

Filter semantics are undefined

A
Verdict
must
Target
new AEP-0024 event triggers, the current draft (equality plus AND as the portable floor)

filter is a map of string. The draft does not say which fields the keys name (event attributes or payload paths), whether values match by equality, or how several entries combine.

Why: in the proof of concept

The concept filters chat events with the key data.user. Because its meaning is open, the manifest filter is only descriptive there and the event router does the real filtering.

Status against the draft

Open. Equality and AND are the portable floor; richer conditions stay in a runtime trigger object (G52) and may only narrow the filter.

Spec 5.2AEP-0021
G43

No duplicate handling and no concurrency for events

A+B
Verdict
must
Target
AEP-0024: concurrencyPolicy and a rate limit on event triggers (A); MUST deduplicate by source and id within a stated window (B)

Webhook retries and at-least-once routers deliver the same event twice, and each delivery can start an execution; at-most-once routers lose events instead (G56). concurrencyPolicy exists only for schedule triggers.

Why: in the proof of concept

The proof of concept rejected a real duplicate as DuplicateEvent. Concurrency control for event-triggered runs is still missing there.

Status against the draft

Open. The manifest fields are category A; deduplication is category B: the spec states the rule, the platform implements it.

Spec 5.2Concept comparison (German)
G44

Who started an event-triggered execution

A
Verdict
must (raised from should)
Target
AEP-0024, plus amending spec 5.2 and 10.3

The draft takes the actor from an authenticated source. For an event that is the bridge that delivered it, not the person who wrote the message. This is a governance hole: initiatorCannotApprove and actorCannotApproveOwnAction (spec 7.6) depend on the initiator, and with actor type system a person who started a run through chat could approve their own request.

Why: in the proof of concept

The trust chain in the proof of concept is only the broker ACLs: only the bridge may publish, and the event carries no signature. The bridge attests "message from slauger", but the run records the actor system.

Status against the draft

Open, raised from should to must. Spec 5.2 gives every event start the actor type system, which cannot hold together with an attested person.

G48

Event runs created by an event router

A
Verdict
into spec, merged with G57
Target
AEP-0019 open question 1, the current draft: spec.event plus an origin (ingress or replay)

A client-created WorkflowRun is a manual start, and runtime-created runs record the trigger only in status. A router such as Argo Events or Tekton Triggers that creates runs for event triggers fits neither role.

Why: in the proof of concept

In the proof of concept an Argo Events sensor creates runs with spec.trigger.type: event, which is non-conforming; the runtime therefore keeps its own run kind instead of the AWP WorkflowRun.

Status against the draft

Open, merged with G57 as AEP-0019 open question 1. The runtime also plans to create event runs itself from a generated trigger object (G52); the ingress origin stays relevant for routers outside the runtime.

Spec 10.8AEP-0019Concept comparison (German)
G52

Runtime trigger objects

B
Verdict
concept
Target
extension of AEP-0021 B6

AEP-0021 B6 attaches runtime bindings to a workflow, but not objects for event routing, CEL filters or rate limits. A hand-written Argo Events sensor has no reference to the workflow and no status.

Why: in the proof of concept

The proof of concept routes events with an Argo Events sensor written by hand. Nothing ties it to the trigger entry it serves, and it reports no status.

Status against the draft

Concept. The object stays implementation-specific; the attachment rules (targetRefs with the trigger index, may only narrow, Accepted) are AWP rules.

AEP-0021
G54

What triggers[].source means

A
Verdict
into spec
Target
AEP-0004 and AEP-0024; remove the row from AEP-0021 B4

In CloudEvents, source is the context in which an event happened (a URI reference). AEP-0021 B4 treats triggers[].source as the name of an event source, with a domain prefix for implementation values.

Why: in the proof of concept

The proof of concept used source as the name of its event source adapter, while the events it receives carry a CloudEvents source of their own. Both readings are plausible from the draft.

Status against the draft

Contradiction confirmed in AEP-0021: B4 lists triggers[].source as a domain-prefixed name, while events carry a CloudEvents source. Agreed: source is the CloudEvents attribute, and the row leaves B4.

G56

Delivery guarantee per event source

B
Verdict
minor
Target
AEP-0021 B1 conformance statement

Whether an event can be lost or arrives more than once depends on the event source and the router in between. A router can silently weaken the guarantee.

Why: in the proof of concept

The Argo Events MQTT event source used by the proof of concept subscribes with QoS 0, which silently downgrades delivery to at most once.

Status against the draft

Open. The other side of G43: at-least-once delivery needs deduplication, at-most-once loses events.

Step isolation: network and credentials

What permissions.network means and how its host list is written, how a platform enforces it, and where model credentials live. Covered by AEP-0023, together with G10.

G47

Manifest requirement versus deployment ceiling

B
Verdict
must
Target
new AEP-0023 step isolation, the current draft

Operators restrict egress outside the manifest (NetworkPolicy, egress proxy, firewall). The draft does not say how permissions.network relates to such limits, or what happens when a runtime cannot enforce a rule. Without a network block, a manifest claims full egress.

Why: in the proof of concept

The proof of concept cannot restrict command-step egress by host name without a proxy and rejects such manifests. Namespaces that deny egress by default do not give what a manifest without network claims, so the concept writes network into every manifest.

Status against the draft

Open. The rule "reject if the platform cannot enforce it" from G51 belongs here.

G49

allowHosts has no syntax

A
Verdict
into spec
Target
AEP-0023

allowHosts is a list of "host names". Subdomain wildcards, ports, IP literals and CIDRs are not defined, so an allowlist cannot be carried from one runtime to another.

Why: in the proof of concept

The proof of concept enforces allowHosts with Squid and uses its notation .example.org and a CIDR mode. The concept marks both as runtime-specific until the spec defines a syntax.

Status against the draft

Open.

Spec 7.5Concept comparison (German)
G50

Allowed hosts that resolve to private addresses

B
Verdict
must (security profile)
Target
AEP-0023: private destinations denied by default after resolution, unless allowed explicitly

An allowed host name can resolve to loopback, private, link-local (cloud metadata) or CGNAT addresses. That opens server-side request forgery and DNS rebinding through an allowlist that looks harmless.

Why: in the proof of concept

The tool proxy of the proof of concept had exactly this hole. It now checks the resolved address at connect time, which covers DNS rebinding by construction.

Status against the draft

Open, for the security profile. Not a blanket ban: agents sometimes need internal services, so an explicit allow in the manifest, within the platform ceiling, still works.

Spec 7.5Spec 12
G51

How network rules are enforced for command steps

C
Verdict
informative
Target
AEP-0023 informative section; G10 merges in

The draft requires runtimes to apply permissions.network to command steps but gives no guidance how. Kubernetes NetworkPolicy matches addresses, not host names (G10).

Why: in the proof of concept

The proof of concept runs an egress proxy per agent workload, fed from allowHosts, and a NetworkPolicy that only allows that proxy. Without the proxy it rejects host-based rules for command steps (G47).

Status against the draft

Open. Informative only; G10 merges in, and the rejection rule belongs to G47.

G61

Where model credentials live

B
Verdict
must (security profile)
Target
AEP-0023 or spec 9, the current draft (not AEP-0008)

The draft does not say where model credentials live. A runtime may hand the provider key to the agent step, where any command or injected instruction can read it.

Why: in the proof of concept

The proof of concept enforces budgets in a model proxy. Whether the key stays there or reaches the step is not covered by the draft, and the proof of concept already found a provider key leak through a model baseURL in its binding.

Status against the draft

Open, for the security profile. Not AEP-0008: its non-goals exclude credentials.

Conversation, state and identity

Context that outlives one message or one execution: reply targets, chat threads, state shared between workflows, and the identity a workflow uses towards other systems.

G45

No reply path

C
Verdict
informative
Target
AEP-0024 informative section

A run started by a chat message should answer in the same thread. The manifest has no way to refer to where the event came from.

Why: in the proof of concept

The proof of concept delivers chat answers with a command step, which needs the thread of the triggering message from the event data.

Status against the draft

Open. Becomes category A if AWP standardizes interaction event types.

G46

Conversation context for event-triggered runs

C now, A later
Verdict
informative in the current draft
Target
AEP-0024 informative; a standard shape after the current draft

A reply in a thread (chat, ticket, mail) starts a run that sees only the triggering message. Follow-up questions lose the conversation.

Why: in the proof of concept

In the proof of concept the chat bridge attaches the earlier messages of the thread to the event. Every source with conversations needs the same, so a common shape keeps workflows independent of the source.

Status against the draft

Informative in the current draft. Normative only: thread context belongs to event.data, is untrusted and classified, and contains personal data. A standard shape later, after the current draft.

A

into spec
Target

Two workflows of one owner share state: a daily run writes what it reported, a chat run reads and writes preferences. AWP has no state at all (G03), let alone shared state.

Models: input to AEP-0008

AEP-0008 (Review) defines a ModelCatalog kind for prices, regions and limits. It names v1alpha3 as its target, written before D20; that now means after the current draft. G59 and G60 are offered as input to it, not as changes to the current draft.

G59

Catalog limits are binding

A
Verdict
into spec
Target
AEP-0008, after the current draft; with G34, which could come earlier, in the current draft

AEP-0008 treats contextTokens and maxOutputTokens as informative. A runtime may ask for more output tokens than the model allows, and the provider rejects the request.

Why: in the proof of concept

A vLLM server rejected every request of the proof of concept until the runtime capped output tokens at the model limit. Its provider profiles confirm the split of AEP-0008: prices and limits in the catalog, endpoint, protocol and credentials in runtime configuration. Price 0 for local models counts as known (G35).

Status against the draft

Input to AEP-0008, after the current draft. G34 (model.parameters.maxOutputTokens) could come earlier, in the current draft.
