AWP v1alpha3: how it fits together

The Agentic Workflow Protocol describes what an agentic workflow does, what it may do and how it is governed and audited. This page explains the current draft for readers who did not follow the discussion: which manifests you write, how they relate, what happens from applying a manifest to a finished run, what the two open spec pull requests add, and how to start as a workflow author or as a runtime implementer.

This site shows a combined preview of the two open spec pull requests, not merged text. Every spec and AEP link goes to the branch preview/pr19-pr20 at 818601c: main of the specification repository with pull requests #20 and #19 merged on top, as the spec will look once both are merged. Status. v1alpha3 is the current draft on main of the specification repository (decision D20: pull request #16 was merged as v1alpha3; v1alpha2 is the step iteration draft of D19). Nothing in it is accepted except step iteration. Both pull requests are open drafts, and their AEPs are Draft and not applied to the v1alpha3 text; a third pull request for event data (AEP-0004) is planned and has no text yet. Every piece below carries its status: in v1alpha3 PR #19 planned platform only. Manifests marked valid or rejected by checker were run through the reference checker at 818601c (the schema is the same as on main); proposals are marked not checked.

Lifecycle: from a manifest to a finished run

What happens when, and who decides. Each line says whether it is in v1alpha3, proposed in PR #19, planned with the AEP-0004 pull request, or left to the platform.

  1. 1Write the manifests

    • in v1alpha3

      A manifest has apiVersion, kind, metadata (name, labels) and spec; governance fields (version, owner, classification, risk) live in spec. Extension fields go into extensions objects with x- keys. status is reserved for the runtime.

    Spec 3.2Spec 4

  2. 2Validate before you apply

    • in v1alpha3

      The reference checker validates YAML restrictions, the JSON Schema and the semantic rules for the profiles you name. Unknown fields and fields of a profile the runtime does not support are errors, not warnings (fail closed).

    Spec 3.3Reference checker

  3. 3Apply and admit

    • in v1alpha3

      The manifest goes into any object store: files, Git, a database, or a Kubernetes API server (one CRD per kind, kubectl apply --validate=strict). A runtime MUST validate every manifest it reads before acting on it and never changes spec. It reports the condition Valid and, once references are resolved, policies loaded and triggers registered, Ready.

    • platform only

      Validation on write (an admission webhook), the binding that places the workflow, and how triggers are registered.

    Spec 3.10Spec 3.11

  4. 4A trigger fires

    • in v1alpha3

      manual: a client creates a WorkflowRun; the actor is the authenticated creator, never a field. schedule: each tick starts at most one execution; concurrencyPolicy (default forbid) and startingDeadline decide about overlaps and missed ticks, and every tick that starts nothing emits trigger.skipped. event: source, eventType and a filter map; the runtime MUST verify the event source. The event data itself cannot reach the steps.

    • PR #19

      AEP-0024: events are CloudEvents 1.0; filter keys are attribute names or data.<path>, matched by equality, all must match; no second execution for the same source and id within at least 24 hours; concurrencyPolicy (default allow) and rateLimit on event triggers; the authenticated source is the actor, and a person attested by a trusted source becomes attestedActor.

    • planned

      AEP-0004: event data under its own root ${{ event.* }} with dataSchema and classification, never mapped to inputs (D7). Amendment of AEP-0019 open question 1: the run object carries the event, set by a trusted ingress or supplied for a test or replay (G48, G57).

    Spec 5.2Spec 10.8AEP-0024 (PR #19)AEP-0004

  5. 5Admit the execution

    • in v1alpha3

      Before anything runs: inputs are validated (a schedule uses defaults), every model is checked against modelPolicy, the environment must be allowed, and a critical risk level needs an approval of the execution itself. A run that cannot start gets phase: rejected and emits no workflow.started.

    • PR #19

      AEP-0023: if the platform ceiling does not allow a destination the manifest needs, or the runtime cannot enforce a network rule for a step type, the runtime rejects before any step runs.

    Spec 5.3Spec 7.4Spec 7.10AEP-0023 (PR #19)

  6. 6Pin what runs

    • in v1alpha3

      At start the runtime resolves the workflow, every referenced Agent and every applicable Policy, computes the digest and keeps exactly these versions until the end, also across retries and waits. Image tags are resolved to the digest of the image index; an image that cannot be resolved fails the execution before any step. workflow.started carries the digest. A GitOps sync during the run changes nothing.

    Spec 10.1AEP-0020

  7. 7Run the steps, isolated

    • in v1alpha3

      Steps form a graph through dependsOn; ready steps run up to maxConcurrency (default 1), forEach fans out over a bounded list. Command steps run in an isolated environment with permissions.network and permissions.filesystem applied; command is never expression-enabled, values come through env. Every action goes through the decision: permissions, then deny rules, then approval. Budgets are checked before every model call and action.

    • PR #19

      AEP-0023: one host syntax for allowHosts (name, *.domain, address, CIDR, optional port); effective network = manifest intersected with the platform ceiling; enforce or reject; under security egress defaults to deny and internal addresses are denied after resolution unless manifest and ceiling both allow them; model credentials are never visible to steps.

    • platform only

      The mechanism: an egress proxy, network policies, a sandbox, a model proxy.

    Spec 5.6Spec 7.5Spec 8.4AEP-0023 (PR #19)

  8. 8Produce outputs

    • in v1alpha3

      A command step writes one file per declared output into $AWP_OUTPUTS; an agent step ends with complete_step. Every runtime accepts at least 256 KiB per output and 1 MiB per step and never truncates. Outputs of failed attempts are discarded. Each output is recorded as artifact.created with its digest.

    Spec 5.6.4AEP-0018

  9. 9Ask people: input and approval

    • in v1alpha3

      Input steps and agents with humanInput ask named people and wait (waitingForInput, profile interaction). Approvals gate actions or steps (waitingForApproval, profile governance); only an authenticated human can approve, an answer is never an approval, and separationOfDuties keeps the initiator from approving.

    • PR #19

      AEP-0024: in a run started by an event, the attested person counts as the initiator, so the rule binds the person who wrote the message, not only the bridge.

    Spec 5.8Spec 7.6Spec 7.8AEP-0024 (PR #19)

  10. 10Keep state for the next run

    • PR #19

      AEP-0025: declared stores with classification, retention and access mode, shared only within one owner; atomic writes; command steps see $AWP_STATE_DIR/<name>. Spec 12: content kept between executions is untrusted input. Today state exists only invisibly in the runtime.

    AEP-0025 (PR #19)

  11. 11Finish, report, audit

    • in v1alpha3

      The run ends succeeded, failed or cancelled; WorkflowRun.status shows phase, steps, usage and the conditions Accepted and Succeeded, never output values or secrets. Audit events (workflow.*, tool.*, policy.*, approval.*, input.*, artifact.*) are the record; under the audit profile they form a hash chain, and a reproducibility record lists everything the run depended on.

Worked examples

Five small manifests in one neutral domain (a concert scout), each building on the one before. Left panes are v1alpha3 and were run through the reference checker at 818601c; right panes mark what a proposal adds and are not checked.

1

A scheduled agent workflow with outputs

in v1alpha3

Every morning a command step fetches venue programs, an agent keeps the concerts that match a taste, and a second command step sends the digest. This is plain v1alpha3 under the core profile.

What it shows

The schedule uses the input default (a schedule supplies no inputs); forbid skips a tick while the previous run still runs. The command writes its output as a file into $AWP_OUTPUTS, the agent ends with complete_step, and values reach the second command through env, never through the command text. The WorkflowRun on the right is a manual start: its creator is the actor, and version is an assertion that fails the request if the workflow has moved on.

Why

Each line maps to one rule a runtime MUST enforce: tick handling (5.2), outputs (5.6.4), no expressions in command (5.6.2), default: deny with one explicit allow (7.5), budget checked before every model call (5.7), image tags resolved and pinned at start (10.1).

2

The same workflow under the security profile

in v1alpha3PR #19

The same workflow, reviewed for the security profile: images pinned by digest and outbound network limited to the venue site and the webhook. The right side shows what AEP-0023 adds.

What it shows

v1alpha3 already has egress: deny with allowHosts and requires digests under security; a tag is rejected (bottom). AEP-0023 defines the entry forms, makes the effective network the intersection of the manifest and a platform ceiling, requires the runtime to enforce it or reject the run before any step, denies loopback, private, link-local and CGNAT addresses after resolution unless both manifest and ceiling allow them, and keeps model credentials out of every step.

Why

Without a syntax the same list means different things on different runtimes; without enforce-or-reject a runtime may silently ignore allowHosts for command steps (G10, G51); an allowed host that resolves to a metadata address is an SSRF hole (G50). Under security, AEP-0023 also changes the default of egress to deny.

3

An event-triggered workflow

in v1alpha3PR #19planned

A chat message in the concerts channel starts a run that answers it. v1alpha3 can start the run but not pass the message; PR #19 defines the event model, the planned AEP-0004 pull request makes the data reachable.

What it shows

AEP-0024: the event is a CloudEvent, source names its producer, filter matches attributes or data.<path> by equality, a second event with the same source and id within at least 24 hours starts nothing (trigger.skipped, reason duplicate, no manifest field), and rateLimit and concurrencyPolicy bound the load. The planned pull request adds ${{ event.data.* }}, dataSchema and classification (AEP-0004) and lets the run object carry the event, from a trusted ingress or as a test or replay (bottom).

Why

Without event data, runtimes map payloads to inputs, which hides that a value comes from an external sender (D7 rejects that). Brokers and webhooks redeliver, so duplicates are real; the reviewed filter stays the upper bound, and runtime filters may only narrow it. Conversation context is untrusted input.

4

State between runs

in v1alpha3PR #19

The scout should report each concert once. Today that memory is a file on a volume the runtime provides, invisible in the manifest. AEP-0025 declares it.

What it shows

Each store has a name, an access mode, a classification (default: the workflow's) and a retention. Command steps find it at $AWP_STATE_DIR/<name>; agent steps only through granted tools. Workflows of the same owner in the same namespace share a store of the same name, the strictest classification applies to every reader, writes are atomic, and the runtime states whether concurrent writers are serialised.

Why

Reviewers cannot see that a workflow keeps data, which class it has or how long it is kept (G03, G53). Content written by one run is read by the next: PR #19 also changes spec 12, so state is untrusted input and a stored chat message cannot become a standing instruction (G58).

5

Human approval and the initiator rule

in v1alpha3PR #19

A newsletter is drafted by an agent and sent only after an editor approves it, and the person who started the run cannot approve it. Approval belongs to the governance profile.

What it shows

The approval step pauses the run in waitingForApproval until an authenticated editor approves; an agent can never approve, and an answer to an input request never counts as one. initiatorCannotApprove rejects an approval by whoever created the WorkflowRun. With PR #19, a run started by a chat message has the bridge as actor and the attested author as attestedActor, and the rule binds that author; a policy can refuse event runs without an attested person.

Why

In v1alpha3 every event start has the actor type system, so a person could start a run by message and approve its request (G44, raised to must). A runtime without the governance profile must reject the manifest instead of running it without approvals (bottom).

Adopt it

Two short checklists. Profiles decide which fields a runtime must understand; a manifest that uses a field of a profile the runtime does not claim is rejected, never run without it.

As a workflow author

  1. Start from example 1: apiVersion: awp.agenticworkflowprotocol.org/v1alpha3, a DNS-1123 metadata.name, spec.version (SemVer), spec.owner.team, and spec.classification if you target the governance profile.
  2. Declare triggers (without them only manual starts are possible); give inputs defaults if a schedule starts the workflow.
  3. Pass values to commands through env, never in command. Write outputs to $AWP_OUTPUTS/<name> or let the agent end with complete_step.
  4. Use permissions with default: deny and explicit allows; limit network with egress: deny and allowHosts; declare secrets by name with the smallest scope, never as values.
  5. Pin images by digest if the workflow must run under the security profile; outside it, tags are resolved and pinned at start.
  6. Choose the profiles from the table and validate: in a checkout of the spec repository run npm ci, then node conformance/awp-check.mjs check --profiles core,governance my.workflow.yaml. node conformance/awp-check.mjs migrate old.yaml converts v1alpha1 and v1alpha2 manifests.
  7. On Kubernetes, install the CRDs from schema/crd/ and apply with kubectl apply --validate=strict; read Valid and Ready in kubectl get workflows. The Helm chart packages a complete example.
  8. Do not rely on proposals yet: ${{ event.* }}, spec.state, rateLimit and the new allowHosts forms are not in v1alpha3 and the checker rejects or ignores their meaning.

As a runtime implementer

  1. Pick the profiles you can meet completely and publish a conformance statement (spec 11.3): limitations, limits, executionObjects. A profile with one unmet MUST cannot be claimed.
  2. Reject, never run partially: an unsupported apiVersion or kind, unknown fields, x- keys outside extensions, fields of profiles you do not support, literal credentials, invalid inputs, models outside modelPolicy, digest mismatches, images that cannot be resolved, image steps if you cannot run containers.
  3. Enforce at run time: the decision algorithm for every action (8.4), budgets before every model call and action, isolated command steps with network and filesystem applied, no expressions in command, the output rules (no symlinks, minimum sizes, no truncation, failed attempts discarded), pinning, approvals only by authenticated humans, the actor of a run from an authenticated source, no secret values to models, logs or audit.
  4. Prepare for PR #19: enforce the effective network or reject before the first step, check resolved addresses, keep model keys out of steps, deduplicate events by source and id for at least 24 hours, write state atomically, treat state and conversation context as untrusted input.
  5. Test your validator with the conformance suite: npm test in the spec repository runs every case, and conformance/v1alpha3/index.json lists expected accept or reject, code and path for your own validator. A runtime test suite is planned; until then conformance statements are self-declarations.
  6. Report gaps the way docs/runtime-feedback.md does: one entry per gap with severity, the proposal and the evidence from your runtime, as an issue or an AEP in the spec repository (D18).
